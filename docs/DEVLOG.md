# 设计记录

> 记录「为什么这么做」以及踩过的坑。代码会变，理由值得留下——
> 半年后想改一个约束时，先看这里有没有已经论证过。

---

## 001 · 时间解析注入 `ref`，而不是读 `Date.now()`

**背景**：时间解析天然依赖「现在」。「本周五」是哪天，取决于今天星期几。

**决定**：`extractTime(text, ref: Date)` —— 「现在」是参数，函数体内不出现 `Date.now()`。

**理由**：

1. 测试可确定性复现。48 条单测全部固定 `ref = 2026-11-04 22:07（周三）`，换机器、换时区、明年再跑都一样。如果读系统时间，测试就是一批定时炸弹。
2. 用户改「基准日」时可以重算（未来做批量补录时用得上）。
3. 纯函数，无副作用，可以放心在 UI 里多次调用。

**代价**：调用方必须记得传 `ref`。可接受——全项目只有一个入口（`parseNotice`）。

## 002 · 规则引擎优先，AI 只做增强

**背景**：这类需求最省事的做法是「把通知丢给大模型，让它返回 JSON」。

**决定**：默认路径是规则引擎；AI 引擎是可选项，未配置密钥时完全静默降级。

**理由**：

1. **可用性**：没配 Key 的人也要能完整用起来（自己装来用、离线环境、公司内网）。
2. **可解释**：「命中关键词『实验报告』」「时间短语『本周五23:59』」这种理由能展示给用户；模型给出的理由只是它自己写的说明。
3. **稳定性**：通知里 70% 的信息高度模式化，规则比模型更稳、更快、更省。
4. **成本**：批量粘贴几十条通知时，不该每次都付费。

**代价**：规则需要持续维护。缓解方式是「样本驱动」：`src/core/samples.ts` 里的真实通知同时服务 UI 示例和单元测试，出一类新写法就加一条样本 + 一条测试。

## 003 · AI 独有的条目置信度封顶 `medium`

**背景**：双引擎合并时，有些条目只有 AI 抽出来、规则没命中。

**决定**：这类条目一律 `confidence: 'medium'` 封顶，理由里写明「请重点核对」。

**理由**：置信度是给用户看的承诺。规则命中的条目能解释为什么，AI 独有条目解释不了——
既然解释不了，就不该给出和别人一样高的置信度。**无法解释的结论不配高置信**，这条比准确率更重要。

---

## 004 · 业务阈值只允许存在一处

**背景**：倒计时颜色（12 小时内红、48 小时内黄）很容易被写进组件，然后在第二个地方再抄一遍。

**决定**：阈值只在 `core/format.ts` 的 `countdown()` 里，返回 `tone: 'normal' | 'warn' | 'danger' | 'overdue'`，组件只消费。

**理由**：同一个数字出现在两处，就是两个数字迟早会不一致。审代码时可以拿这条当检查项：
**组件里出现比较大小的业务判断，就是 bug 的开始。**

---

## 005 · 不做 UI 框架，样式手写

**背景**：Ant Design / Element / Tailwind 都能更快出画面。

**决定**：手写 CSS + CSS 变量（`src/styles.css` 约 900 行），零 UI 依赖。

**理由**：

1. 体积：典型组件库会让包体翻 2–3 倍，而这个工具求的是「打开就快」。
2. 视觉：组件库的默认长相大家一眼就认得，容易撞脸。
3. 可控：全部样式在一个文件里，改主题改一处变量即可。

**代价**：所有交互状态（hover / focus / disabled / 空状态 / 窄屏）都得自己写，代码量不小。
如果将来要支持主题切换或更复杂的组件，再考虑引入无样式（headless）库。

---

## 006 · 本地优先，不做后端

**背景**：班级群通知里常有学号、手机号、成绩、身份证号（助学贷款类通知尤其多）。

**决定**：无后端、无账号，数据只落 IndexedDB；默认不发任何网络请求（除用户主动配置的 AI 引擎）。

**理由**：隐私不是「加分项」，是这类工具能不能被信任的前提。学生愿意把真实群消息贴进来的唯一理由，就是知道它不会被上传。

**代价**：没有云同步、没有多端共享、换浏览器数据就没了。缓解：导出 / 导入 JSON 备份。

## 踩坑记录

### CI 上 pnpm 11 + Node 20 直接崩（`node:sqlite`）

**现象**：GitHub Actions 里 `ci` 和 `pages` 两个工作流都在「准备 Node.js」这一步失败，
`pnpm install` 之前就挂了。报错关键两行：

```
warn: This version of pnpm requires at least Node.js v22.13
Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: node:sqlite
```

**原因**：pnpm 11 用 `node:sqlite`（Node 22.5 起才有的内建模块）做存储索引，
而工作流把 `node-version` 钉在了 20。pnpm 一启动就崩，于是 `setup-node` 的 `cache: pnpm`
（内部要跑 `pnpm store path`）跟着失败，看起来像「Node 安装失败」，其实 Node 装得好好的。

**解决**：工作流改用 Node 22，`package.json` 的 `engines` 从 `>=18` 提到 `>=22.13`，
并加 `packageManager: pnpm@11.28.5` 锁版本。

**教训**：报错位置（这里显示「准备 Node.js」失败）和真实原因（pnpm 版本与 Node 不兼容）可以离得很远。
看到「某步骤失败」先别改那一步，先读它打印的完整输出。

### pnpm 11 拦截构建脚本，依赖装不完

**现象**：`pnpm install` 报 `ERR_PNPM_IGNORED_BUILDS: esbuild` 并以退出码 1 结束，
但依赖看起来「装上了」；随后 `vitest` 启动时报 `Cannot find package '@vitest/utils'`。

**原因**：pnpm 10+ 默认不执行依赖的安装脚本；install 因此非零退出，中途停下，`node_modules` 不完整。
而报错出现在下游（vitest），很容易误判成「vitest 坏了」。

**解决**：在 `pnpm-workspace.yaml` 里放开（pnpm 11 起不再读 `package.json` 的 `pnpm` 字段）：

```yaml
onlyBuiltDependencies:
  - esbuild
dangerouslyAllowAllBuilds: true
strictDepBuilds: false
```

**教训**：装依赖失败时先看 install 本身是否成功，不要被下游报错带跑。

### vitest 2 与 vite 6 的类型冲突

**现象**：`tsc --noEmit` 报 `Plugin<any>` 不可赋值——两套 `UserConfig` 打架。

**原因**：vitest 2.1 在类型层面绑定 vite 5，项目用 vite 6。

**解决**：升级到 vitest 3（与 vite 6 对齐），并把测试配置拆成独立的 `vitest.config.ts`
（单测只覆盖 `core/` 纯函数，不需要 react 插件，跑得更快）。

**教训**：不要用 `as never` / `as any` 压掉类型冲突。压掉的冲突会在运行时以更贵的方式回来。

### PowerShell 5.1 会把 UTF-8 文件读成 GBK

**现象**：用 `Get-Content` 看中文文件显示乱码，`ConvertFrom-Json` 甚至解析失败。

**原因**：Windows PowerShell 5.1 默认按系统代码页（中文系统为 GBK）解码，不是 UTF-8。
文件本身没问题，是读取端错了。

**影响**：如果**写入**端也用了同样错误的编码，仓库里就会混进 GBK 文件，推到 GitHub 后中文变乱码或问号。

**解决**：仓库加 `scripts/check-encoding.py` 自查，并纳入 CI（`python3 scripts/check-encoding.py`）。
`.gitattributes` 统一 LF，`.editorconfig` 固定 UTF-8。

### 一次真实 bug：寒暄被当成了待办

**输入**：「大家早上好呀，今天天气不错」
**现象**：解析出一条待办（因为命中了「今天」，有日期）。

**定位**：原判据只有「没有时间就不算待办」，漏了「有时间但没有行动要求」。

**修复**：加一条——**纯日期 + 未知类型 + 无截止语义 + 无具体钟点 = 不是待办**。

```ts
if (kind === 'other' && !hasDeadlineWord && !hit?.hasClock) return null
```

**教训**：解析类功能里，「不该抽出来的东西被抽出来」比「漏抽」更伤信任——
用户会立刻觉得这工具在瞎编。判据要从严。

### 一次真实错误：我写了自相矛盾的断言

**现象**：某条测试同时断言「结果是 2026-10-01」和「年份是 2027」，必然失败。

**定位**：引擎按规则（已过去的月日 → 按明年算）给出了 2027-10-01，**引擎是对的，测试是错的**。

**修复**：改测试，不改引擎，并把这条规则写进 README「已知限制」。

**教训**：测试失败时先假设自己错了。如果反过来「改实现去迁就测试」，就会把错误固化成「通过」。

## 想加一种新的时间写法？

1. 在 `src/core/samples.ts` 加一条包含该写法的真实通知；
2. 在 `src/core/ruleParser.test.ts` 或 `time.test.ts` 写断言（一定注入固定 `ref`）；
3. 跑 `pnpm test` 确认失败；
4. 改 `src/core/time.ts` 的 `resolveDate` / `resolveClock`，让测试变绿；
5. 顺手确认 UI 上「为什么这么判断」的理由说得清。

做到这五步，这次改动就是可回归的。
